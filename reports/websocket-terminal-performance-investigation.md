# WebSocket, tmux terminal performance, and planner reliability

## Scope

This report investigates two related symptoms:

1. tmux-backed workspace tabs (Shell, agents, Neovim, Lazygit, and Process panes) are slow to become usable and terminal output feels less responsive after the unified UI-state WebSocket work;
2. invoking the `kiwi-code-planner` fork can fail with only `WebSocket error`, leaving no published plan and too little information to diagnose the failure.

This report began as an investigation and implementation plan and now also records the completed implementation and isolated validation. No production process, port, data directory, or canonical `tmux -L kiwi-code` server was inspected. The initial investigation could not run a real tmux timing probe under the active sandbox; after the sandbox was disabled, the implementation was exercised with fresh temporary data, fresh loopback ports, and unique non-production `kcv-*` tmux sockets.

## Executive conclusion

WebSocket is still the correct browser transport for interactive terminals. It is full-duplex, ordered, binary-capable, widely supported, and adds negligible protocol overhead compared with the current tmux setup and rendering work. SSE cannot carry terminal input, browser `fetch` does not provide a comparably portable bidirectional stream, raw TCP is unavailable to a normal browser, and WebTransport would require an HTTP/3/TLS deployment plus a second protocol without addressing the current bottlenecks.

The terminal bytes should **not** be moved onto `/api/state`. Separate terminal sockets isolate high-volume terminal traffic from UI state and from other panes. Multiplexing them would introduce avoidable head-of-line blocking and make one stalled xterm capable of delaying unrelated state.

The likely performance regression is a combination of:

- expensive, globally serialized tmux setup before the first terminal byte;
- an initial burst of state-topic work that competes with the active terminal for tmux subprocesses and browser main-thread time;
- no application-level backpressure between the PTY and xterm.js;
- one WebSocket frame per PTY read and JSON encoding/decoding for every input chunk;
- broad React updates and strict state-snapshot decoding on the same browser thread that parses and renders xterm output.

The planner failure is not generated by the planner extension's internal request code. `run_forked_skill` uses authenticated HTTP requests to create and poll a child; the WebSocket is the parent Pi Native transport carrying the tool call and its updates. The current code discards close details at several layers, so the exact failure cannot be proven from the generic message. There are also real recovery gaps if the parent socket is lost after a child is committed but before the creation response reaches the tool.

## What changed and what did not

The relevant unified-state changes are commits `cbcf90f` and `f8ab7ca`.

### Verified from the diff

- `web/src/components/organisms/TerminalSession.tsx` did not switch terminal bytes to the new state socket. Each terminal still owns a dedicated WebSocket.
- `internal/server/websocket_transport.go` still copies PTY output directly to that terminal's socket as binary messages.
- The old global and thread SSE consumers were replaced by independently opened `/api/state` channels.
- The new client strictly validates every state snapshot with Effect schemas on the browser main thread.
- `App.tsx` removed the old `sameProjects` and `sameProfiles` structural guards and copies ready subscription data into React state.
- `TerminalWorkspace.tsx` copies every `thread.status` projection into several local state values.
- Expensive state-topic handlers are started independently in goroutines, so their initial reads can arrive as a burst instead of being naturally sequenced by one SSE handler.

This means the regression is not evidence that WebSocket framing is intrinsically slower than SSE. The new state architecture changed scheduling, decoding, and render pressure around the existing terminal socket.

## Current terminal critical path

### Browser

`TerminalSession` performs the following when a tool is opened for the first time:

1. waits for a `requestAnimationFrame`;
2. constructs xterm, Fit, WebLinks, and Canvas addons;
3. opens and fits xterm;
4. creates a new WebSocket;
5. marks the pane `open` on the WebSocket handshake, before tmux setup has finished;
6. sends JSON resize and JSON input messages;
7. calls `terminal.write` once for every incoming WebSocket message.

Opened tool panes remain mounted, so a normal repeat switch between already-open tools should not reconnect. If repeat switches still pause, measurements should distinguish a real reconnect from browser main-thread jank or an xterm backlog.

### Server

`terminalHandler.serve` upgrades first, then does the expensive work. For a shared-tools pane it may:

- acquire the global `terminalHandler.sessionMu`;
- acquire the per-thread durable mutation lock;
- reconcile stale linked views and coding-agent windows;
- run multiple `has-session`, `list-sessions`, `list-windows`, `display-message`, and option commands;
- reapply four window options plus `rename-window`, even for an already tagged fixed window;
- find the target window again after ensuring it;
- record session activity;
- create a temporary one-window linked view using a dummy session, link, verification, dummy removal, and two separate metadata writes;
- set the server clipboard option;
- finally spawn `tmux attach-session` under a PTY.

The shell path is shorter, but it still enters the global lock and can wait behind unrelated shared-tool, process, native-agent, stop, or view operations. A backend restart can reconnect several retained panes simultaneously, turning this global lock into a visible queue.

### Streaming

`startPTYWebSocketBridge` currently:

- allocates a 32 KiB read buffer;
- immediately writes one binary WebSocket message for every `ptmx.Read` result;
- has network backpressure only when the socket write itself blocks;
- has no knowledge of xterm's parser/render queue;
- accepts terminal input as JSON text and unmarshals it for every `onData` callback.

This protects server memory only at the network layer. A browser can accept WebSocket messages much faster than xterm can parse and paint them.

The installed xterm.js 5.5 source explicitly warns that terminals typically become unresponsive above roughly 500 KiB of pending write data and tells embedders to implement flow control. Its emergency discard watermark is about 50 MiB. Kiwi Code currently has no such flow control, so a fast command can build a large browser-side queue, delaying keystrokes and rendering long after the network transfer completed.

## State work that can contend with terminals

### Backend contention

Opening the application creates global state subscriptions, including `processWebServers`. That topic:

- installs process-session control-mode watchers for every visible thread;
- scans every project's threads to build its initial snapshot;
- runs tmux existence/window commands per thread.

The active workspace also opens `thread.status`, which reads Git state, process windows, and shell windows and installs two tmux watchers.

`Server.notifyThreadStatusChanged` invalidates both `thread.status` and the global `processWebServers` projection. A tool window creation can therefore trigger a full cross-project process scan while its terminal is still being prepared. The pre-WebSocket SSE implementation also performed global process reads, so this is not wholly new, but independent state channels make the initial and invalidation work more concurrent and less naturally ordered.

### Browser contention

All of the following share the renderer main thread:

- JSON parsing for state and native-agent WebSockets;
- Effect schema validation;
- React subscription notifications and commits;
- xterm parsing and Canvas rendering;
- terminal keyboard and resize handlers.

Agent heartbeats update timestamps every few seconds. Large project, usage, process, or native-agent snapshots can therefore cause periodic long tasks even though terminal bytes use another socket.

## Recommended transport architecture

Keep three traffic classes separate:

1. `/api/state`: low-frequency authoritative UI snapshots, text JSON;
2. one terminal WebSocket per visible tmux attachment: latency-sensitive binary PTY data and small control frames;
3. Pi/Claude Native WebSockets: structured RPC event streams with their own lifecycle and backpressure policy.

Do not enable per-message compression on terminal sockets. Terminal escape streams are often compressible, but compression adds CPU, buffering, and latency and can worsen contention on the same host. Keep TCP no-delay behavior and verify it in an integration test rather than adding arbitrary flush sleeps.

WebTransport should only be reconsidered if measurements on a remote, lossy network show TCP head-of-line blocking between independent streams to be the dominant cost. It is not justified for the current local/LAN architecture.

## Implementation plan

### Phase 1: add measurements before changing behavior

#### Server timing

Add opt-in terminal lifecycle instrumentation around `terminalHandler.serve` and `serveTmuxBrowserTerminal`:

- request accepted / WebSocket upgraded;
- mutation lock acquired;
- canonical target resolved;
- linked view ready;
- PTY attach process started;
- first PTY read;
- first WebSocket output write;
- cleanup completed.

Use monotonic durations. Do not log prompts, terminal bytes, paths, environment values, or capabilities. Include only project/thread/tool identifiers already used by server diagnostics and a generated connection ID.

For protocol-v2 clients, send a text control envelope such as `terminal_ready` only after the PTY bridge is ready. Keep terminal output binary. The frontend can then distinguish network handshake time from actual terminal readiness; its current `open` status is premature.

Relevant files:

- `internal/server/terminal.go`
- `internal/server/tmux_browser.go`
- `internal/server/websocket_transport.go`
- `web/src/components/organisms/TerminalSession.tsx`

#### Browser timing

Record development-only performance marks for:

- tab activation;
- `TerminalSession` effect start;
- socket `open`;
- `terminal_ready`;
- first output event;
- first xterm write callback;
- maximum pending xterm bytes.

Log whether a supposedly warm tab created a new `TerminalSession` or socket. This separates reconnection from render starvation.

#### Isolated benchmark matrix

Run every live measurement with fresh loopback ports, a temporary data directory, `-mode development`, `-add-current-directory`, and a unique non-production tmux socket.

Measure at least:

- fresh and warm Shell;
- fresh and warm Neovim/Lazygit;
- an existing terminal agent;
- a Process window;
- one pane versus four simultaneous reconnects;
- 1, 10, and 50 persisted threads;
- state subscriptions enabled versus a diagnostic run with expensive projections disabled;
- 1-byte input echo p50/p95;
- sustained 1 MiB and 10 MiB output, frame count, time-to-render, and peak pending xterm bytes.

Use command-count assertions with a fake tmux executable for deterministic regressions, and real tmux only in explicitly isolated integration tests. Performance budgets should be broad enough for CI variance but should fail on accidental extra command rounds or unbounded queues.

### Phase 2: remove tmux work from the first-byte path

Implement the lowest-risk reductions first and remeasure after each one.

1. **Do not reconfigure an already tagged fixed tool window on every attach.**
   - `tmuxToolWindow` already reads `@kiwi-code-tool`.
   - Treat a matching tag as evidence that fixed-window configuration completed.
   - Keep the legacy name-only fallback and configure that window once during adoption.

2. **Return the resolved target from the ensure operation.**
   - Avoid a second `tmuxToolWindow` query in `serve`.
   - Include the pane/server PID in the same format read so view creation can guard against ID reuse.

3. **Batch safe tmux command sequences.**
   - Apply fixed-window options and rename in one tmux command sequence.
   - Apply linked-view metadata in one sequence.
   - Prototype collapsing dummy-view creation/link/replacement only if tests prove the same one-window isolation and incarnation checks.
   - Preserve `kiwi-code-view-` naming and all stable canonical session/window identities.

4. **Move nonessential bookkeeping after PTY readiness.**
   - An attached view already prevents inactivity cleanup.
   - Record `@kiwi-code-last-used` immediately after attach rather than before first output.
   - Configure clipboard once per tmux server incarnation, not for every connection. Invalidate the cache if the isolated tmux server PID changes.

5. **Avoid full stale-view reconciliation on every warm attach.**
   - Reconcile once per thread per backend incarnation, or during a bounded background startup pass.
   - Invalidate that success marker when view cleanup fails or an overlapping backend is detected.
   - Keep all current adoption and process-preservation tests; never trade startup speed for killing an uncertain process.

6. **Replace global mutation serialization with keyed locking.**
   - The durable mutation manager already has a per-thread identity.
   - Split `sessionMu` responsibilities into a small state mutex (stop maps and active-view bookkeeping) plus per-thread mutation locks.
   - Operations on unrelated threads should proceed concurrently.
   - Project-wide stop must acquire thread locks in stable order or use an explicit project barrier to avoid deadlocks.
   - Document and race-test the lock order.

This last item is the highest-impact but highest-risk setup change. It also prevents unrelated terminal setup from delaying Pi Native child creation, including planner forks.

### Phase 3: add terminal protocol flow control and reduce frame overhead

Negotiate a terminal protocol version in the query string so existing headless and older clients continue to work.

#### Binary input

For protocol v2:

- send xterm `onData` payloads as UTF-8 binary frames;
- reserve text frames for JSON control messages (`resize`, credit acknowledgements, and readiness);
- continue accepting the existing JSON `{type:"input"}` form for compatibility;
- preserve exact UTF-8 bytes and test multibyte text, escape sequences, paste, and NUL-containing input.

This removes `JSON.stringify`/`json.Unmarshal` from the keystroke path and avoids JSON escaping expansion.

#### Bounded PTY output batching

Add a small output aggregator between PTY reads and WebSocket writes:

- cap a frame at 32–64 KiB;
- drain already queued PTY chunks immediately;
- allow at most approximately 0.5–1 ms of intentional coalescing, subject to measurement;
- flush immediately for interactive echo if batching worsens p95 input latency;
- stop all producer/consumer goroutines cleanly on PTY, socket, or handler shutdown.

The goal is fewer browser events and xterm write callbacks, not large latency-oriented buffering.

#### Credit-based xterm backpressure

Implement a hard application window, initially 256–512 KiB:

1. the server counts bytes sent but not acknowledged;
2. each browser call to `terminal.write(data, callback)` acknowledges those bytes only from the callback, after xterm parsed the chunk;
3. the server pauses PTY-to-WebSocket forwarding when outstanding credit reaches the limit;
4. input, resize, pings, close frames, and acknowledgement handling continue while output is paused;
5. a stopped connection unblocks all waiting goroutines;
6. acknowledgements are ordered, bounded, and cannot underflow the counter.

Batch small acknowledgements to avoid replacing output-frame overhead with control-frame overhead. Hidden panes should naturally receive less data when their parser/render path slows instead of accumulating unbounded browser memory.

Add tests for:

- a stalled client never exceeding the configured output window plus bounded channel capacity;
- resume after acknowledgement;
- no deadlock when close occurs while paused;
- final PTY bytes delivered before a normal close;
- a healthy client retaining low interactive latency during a large output stream.

### Phase 4: reduce state-channel interference

1. **Make process-web-server invalidation targeted.**
   - Do not rebuild every thread's process projection for an unrelated shell/tool status change.
   - Cache the projection per project/thread.
   - Refresh only the process session identified by its control-mode watcher or process API mutation.
   - Build the global topic by joining cached per-thread projections.

2. **Prioritize interactive terminal work over snapshot reconciliation.**
   - Bound concurrent expensive state reads.
   - Coalesce invalidations while a read is active.
   - Avoid launching dozens of `tmux has-session` processes at application startup.
   - Prefer watcher-maintained cache state over polling where correctness permits.

3. **Restore structural guards in React.**
   - Avoid replacing `projects`, profiles, and thread-status projections when their semantic contents did not change.
   - Update only the status slice that changed rather than setting processes, branches, windows, workflows, and plans together.
   - Stabilize callbacks passed to terminal panes and consider `React.memo` for `TerminalSession` after profiling.
   - Use React transitions for noninteractive sidebar refreshes.

4. **Profile strict schema decoding.**
   - Keep boundary validation for correctness.
   - If traces show multi-millisecond decoding of large snapshots, move state JSON parsing/validation to a Worker or reduce snapshot size.
   - Do not remove validation based on assumption alone.

5. **Compact native-agent streaming separately.**
   - Pi RPC `message_update` and `tool_execution_update` contain accumulated values, not deltas.
   - Measure bytes per completed response; long responses can become quadratic on the wire and in JSON parsing.
   - If confirmed, add a browser protocol that sends deltas plus periodic authoritative snapshots while retaining raw RPC internally for run tracking.

### Phase 5: diagnose and harden planner fork failures

#### Planner data path

`internal/server/pi-skill-forks.ts` does not open a WebSocket. It:

1. `POST`s `/skill-forks` with the inherited model and thinking level;
2. polls `/children/{id}/runs/{run}` every 750 ms;
3. emits a Pi tool progress update on every poll;
4. closes the retained child after settlement;
5. expects the child planner to publish through `POST /plans`.

Those HTTP operations already convert fetch and HTTP failures into descriptive messages. Therefore an outer result containing only `WebSocket error` points to the parent Pi Native connection or the API/tool harness carrying that tool call, not to an error deliberately thrown by the planner extension.

#### Current diagnostic gaps

- `servePiNative` silently returns for many read/write/peer failures.
- The browser's native-agent `error` handler can only report the opaque WebSocket error event.
- Its `close` path does not retain or display `code`, `reason`, or `wasClean`.
- A slow Pi event subscriber is intentionally closed with `CloseTryAgainLater`, but that useful reason is not surfaced to the user.
- `run_forked_skill` emits unchanged progress every 750 ms and does not include a durable operation ID in errors.
- `_toolCallID` is ignored, so child creation is not idempotent from the tool's perspective.
- A parent transport loss can abort the creation fetch. If the server commits the child after the response becomes undeliverable, the tool never learns the child ID. The child can appear in the sidebar while the caller sees only a transport failure.
- There is no request-cancellation regression test around the commit boundary in `createChildThreadAuthorized`.

#### Planner reliability changes

1. **Surface WebSocket close diagnostics.**
   - Log server-side termination category, connection ID, project/thread, close code, and sanitized reason.
   - Record the browser `CloseEvent` fields in the native-agent activity panel and console.
   - Distinguish backend restart, normal pane close, protocol error, pong timeout, slow subscriber, and unexpected network loss.
   - Never log prompts, tool arguments, capabilities, or model output.

2. **Add an idempotent fork request ID.**
   - Pass the Pi `toolCallID` in the `POST /skill-forks` body.
   - Key it by project, parent thread, and request ID.
   - Retrying a lost creation response must return the same child/run rather than creating another child.
   - Retain enough operation state to recover across a backend restart if child creation itself is durable.

3. **Define cancellation at the transaction boundary.**
   - Check request cancellation before persisting a new child.
   - Once the child is committed, treat it as a durable operation even if the HTTP response or parent socket is lost.
   - Let an explicit cancel call the existing stop endpoint; do not conflate a transient transport loss with user cancellation.
   - If Pi's tool `AbortSignal` cannot distinguish those causes, have the backend own the fork lifecycle and expose a separate explicit stop operation.

4. **Make polling resilient after creation.**
   - Retry transient GET failures with bounded exponential backoff and jitter.
   - Do not retry non-idempotent creation without the request ID above.
   - Include child ID, run ID, last successful phase, and a direct recovery instruction in any final error.
   - Leave a settled or unknown child retained rather than hiding it.

5. **Reduce progress traffic.**
   - Emit on state change and then at a low-frequency heartbeat (for example every 5 seconds), not every 750 ms with identical content.
   - Keep polling independently if sub-second completion detection is desired.

6. **Let the planner publish independently of the parent socket.**
   - After a committed child starts, a parent UI/WebSocket reconnect must not prevent `publish_thread_plan` from reaching the backend.
   - On parent reconnection, recover the tool operation by request ID and return the published plan or the retained child failure.

7. **Add end-to-end failure tests.**
   - Drop the skill-fork creation response after commit, retry it, and assert exactly one child.
   - Cancel before persistence and assert no child.
   - Disconnect the parent Pi Native socket while the child runs; assert the child settles and can publish a plan.
   - Force the Pi event subscriber backlog limit and assert the close code/reason is visible.
   - Restart the isolated backend during a fork and verify operation recovery.
   - Inject one transient poll failure and verify the tool completes without duplicating work.
   - Verify explicit cancellation still stops and retains the child.

## Implementation and validation status

The plan was implemented with the following notable details:

- terminal protocol v2 now provides binary input/output, an explicit `terminal_ready` control frame, bounded output coalescing, and a 384 KiB ACK-based xterm parsing window;
- tmux setup returns and reuses tagged targets, batches fixed-window and view configuration, moves bookkeeping after readiness, preserves stale-view adoption, and permits unrelated thread setup to proceed concurrently under durable per-thread mutation leases;
- clipboard forwarding is reasserted in the same tmux command invocation as `attach-session`, rather than cached, because users and nested tools can change the server option without restarting tmux;
- expensive global process projections are cached and invalidated per thread, and state reconciliation yields briefly to active terminal setup;
- redundant React state replacement is guarded and noninteractive subscription updates use transitions;
- adjacent cumulative Pi `message_update` and `tool_execution_update` events are coalesced for browser subscribers without dropping surrounding lifecycle events;
- Pi/Claude native close diagnostics retain useful close information;
- forked-skill requests persist the Pi tool-call request ID, deduplicate creation retries, retry transient creation/poll failures, and reduce unchanged progress traffic to low-frequency heartbeats.

Real-browser validation used `http://127.0.0.1:54730`, temporary isolated data, and tmux socket `kcv-54730-77a86f84`. Two unrelated fresh Shell sessions reached `terminal_ready` concurrently in 25 ms and 27 ms (27 ms wall-clock total). The active browser Shell reached server readiness in 23 ms and first output in 32 ms; a fresh Neovim pane reached readiness in 79 ms and first output in 86 ms. The browser negotiated protocol v2 for every terminal, exchanged binary input/output and ACK frames, executed a Shell command, switched Shell → Neovim → Shell without reconnecting Shell, and reloaded with the tmux output replayed. Console errors and relevant failed requests were empty; expected aborted activity-touch requests during page teardown were classified separately. The isolated application, data, and tmux server were removed afterward.

Automated validation passed:

- `go test ./... -count=1`;
- `go test -race ./internal/broadcast ./internal/project ./internal/server -count=1`;
- `go vet ./...`;
- `cd web && npm test` (117 Node tests and 29 Vitest tests);
- `cd web && npm run build`;
- repeated real-tmux protocol-v2 backpressure, stale-view adoption, clipboard, and concurrency tests.

The real-tmux backpressure integration test withholds acknowledgements during a 700,000-byte stream, verifies delivery remains within the configured credit window, acknowledges the parsed bytes, and verifies the trailing output is delivered. Full backend-restart recovery of an already-running planner model remains a larger lifecycle feature; the implemented durable request identity prevents duplicate child creation and returns retained-child recovery information when the in-memory run cannot be recovered.

## Suggested acceptance targets

Set final thresholds from the Phase 1 baseline on representative hardware. Initial product goals should be:

- warm tab switches perform no network reconnect and become interactive in the next paint;
- warm existing-session attachment requires no repeated fixed-window configuration;
- unrelated thread setup does not block the active thread;
- input echo p95 remains below one animation frame on loopback while moderate output is streaming;
- pending xterm data remains bounded below the chosen credit window;
- no terminal output is lost during backpressure;
- a planner child is never duplicated or orphaned merely because a creation response was lost;
- every abnormal native-agent WebSocket close reports a useful category and close code/reason;
- a transient parent WebSocket loss does not prevent an already committed planner child from publishing its plan.

## Recommended execution order

1. Add timing and close-reason observability.
2. Reproduce and capture a baseline in an isolated stack.
3. Apply the low-risk tmux command reductions and move bookkeeping off the first-byte path.
4. Add terminal protocol v2 batching and credit-based flow control.
5. Target/collapse expensive state reads and reduce React churn.
6. Split global terminal locking only after command-level wins are measured.
7. Add planner request idempotency and durable recovery, then improve polling and progress updates.
8. Re-run the complete browser, headless, race, restart, and failure-injection matrix.
